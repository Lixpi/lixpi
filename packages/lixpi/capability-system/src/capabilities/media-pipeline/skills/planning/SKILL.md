---
name: media-pipeline-planning
description: Plan typed media dependencies and preserve the boundary between discussion, saved drafts, and authorized execution.
---

Use the accepted user request to identify the requested outcome, source references, and constraints. A question about a workflow is discussion. It does not authorize saving an Artifact or generating media. A request to save a plan authorizes a draft. Execution requires the runtime's separate action grant.

Read a referenced pipeline with `get_pipeline` before changing it. Build nodes from the authorized installed operation catalog. Use each operation's exact parameter schema and typed input and output ports. An operation advertised by model metadata is unavailable unless the runtime catalog includes its executor and usable route.

Represent shared work as one dependency node. Connect each required input to one frozen source or one upstream output port. Do not duplicate a shared dependency to create parallel branches. Preserve the user's source references, ordering, exclusions, and other constraints in each revision. Never invent an Asset reference, source revision, output, provider route, or executable code.

For existing media in a sequence plan, `resolve_sequence_source` reads immutable source metadata without creating or editing a sequence. Supply its exact Asset ID and a local source ID; omit `renditionId` to use `original`. Copy the returned metadata and keep the discovered Asset revision when building the frozen pipeline source. A saved draft describes sequence creation and export as nodes; do not call `create_sequence`, `patch_sequence`, or `export_sequence` to prepare a draft.

For a `sequence.create` node, follow its catalog timing and output defaults. New sequences use 240000 ticks per second and default to 1920 by 1080 pixels at 30 frames per second. A five-second held image clip needs `duration: 1200000`, with `sourceIn: 0` and `sourceOut: 0`. Do not use the source's time base for the sequence duration. Set requested output dimensions explicitly with a `set-properties` operation whose `values` contain `width` and `height`. Source dimensions never resize the output frame. Check the saved node parameters against the requested duration and dimensions before reporting the draft ready.

To create a draft, call `save_pipeline` with `baseRevision: 0`, a stable `clientMutationId`, and no `pipelineId`. Put the requested display name in `patch.name`; the server assigns the pipeline ID. Supply the complete initial plan, including `constraints`, `sources`, `nodes`, `edges`, `executionPolicy`, and `outputBindings`, using empty lists where appropriate. For later edits, use the returned pipeline ID and current base revision. A patch replaces only the named plan fields; omitted constraints and references remain unchanged. Preserve unsupported steps as explicit draft gaps instead of quietly dropping them or substituting a different operation. Fix reported structural or source-access errors before saving. A creation-input error is not a permission denial and does not justify switching to execution tools.

For an explicitly requested comparison, `save_pipeline_matrix` expands complete prepared prompt variants across selected image model IDs into at most 32 independent image steps. To have the user's selected reasoning models prepare the variants, use `prepare_pipeline_matrix`. That tool validates all selected reasoning routes before calling them, uses the accepted turn's model budget, and preserves native responses for recovery. The matrix preserves each selected model and prompt without substituting a route. Both tools save drafts; image generation still requires authorized submission. Existing constraints and source snapshots remain unless the request explicitly replaces them.

Use `submit_pipeline` only when the user has requested execution and the runtime grants the required families and targets. Submit the exact saved revision. A pending result means work was accepted, not that media exists. Report completed outputs only from durable receipts. A provider outcome marked unknown requires reconciliation and must not be retried as a new paid operation. Stop or superseding instructions invalidate continuation authority even if already submitted work later completes.

For an explicitly requested retry, inspect the settled execution with `get_operation`, then use `retry_pipeline` with failed root node IDs and a new stable attempt ID. It retries those nodes and their downstream branch while retaining successful dependencies and independent outputs. It rechecks source snapshots and the current execution grant. Repeating the same attempt ID cannot repeat its provider calls. An uncertain provider outcome must be reconciled before retrying any branch.
