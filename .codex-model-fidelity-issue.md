# Knowledge share: synchronized model fidelity metadata and exact model IDs

## Purpose

This issue records the implementation and design decisions around two related model-catalog changes:

1. image-input fidelity is now declared per model by the NEX AI-model synchronization workload and consumed dynamically after routing;
2. Anthropic models discovered through Bedrock retain their exact dated snapshot IDs, so persisted selections continue to resolve by exact DynamoDB key.

This is a knowledge-share issue, not a request for a PR.

## Why this was needed

Character Creator uses a source image as the identity/style reference. A photographic source must remain photorealistic through the final fidelity pass. The runtime therefore needs to know whether the selected image model provides high-fidelity reference-image handling.

The first implementation inferred support in API/provider code from strings such as provider name and `gpt-image-*` model prefixes. That was the wrong ownership boundary: provider/model-specific capability data belongs in `services/nex/workloads/ai-models-synchronization`, while API routing and providers should consume the synchronized model record without knowing individual model names.

Separately, the Bedrock-backed Anthropic listing path normalized a concrete ID such as `anthropic.claude-haiku-4-5-20251001-v1:0` to `claude-haiku-4-5`. That removed the date from the synchronized catalog. Existing persisted selections still referenced `Anthropic:claude-haiku-4-5-20251001`, so exact `AiModel.getAiModel()` lookup failed. The fix is in synchronization; there is deliberately no API lookup fallback.

## Design invariants

- `services/nex/workloads/ai-models-synchronization` is the source of truth for model-specific fidelity behavior.
- API routing and providers consume metadata from the routed model record; they do not test provider/model names.
- Missing or `standard` fidelity metadata fails closed for reference-conditioned Character Creator runs.
- `requestValue` is distinct from effective fidelity. Some models are high fidelity automatically and must not receive an `input_fidelity` request field.
- Persisted model selections resolve by exact catalog key. The API does not retry aliases, strip snapshot dates, or select a fallback model.

## Shared metadata contract

`packages/lixpi/constants/ts/types.ts` defines the policy:

~~~ts
export type ImageInputFidelityPolicy = {
    level: 'standard' | 'high'
    requestValue?: 'low' | 'high'
}
~~~

The model catalog record carries it as optional metadata:

~~~ts
export type AiModel = {
    // ...
    // Effective fidelity for reference-conditioned image generation. A provider
    // request value is included only when the model API requires one.
    imageInputFidelity?: ImageInputFidelityPolicy
}
~~~

`level` is the capability used by routing. `requestValue` is only the provider request value to emit when the API requires explicit configuration.

## Model declarations in NEX synchronization

The OpenAI image-family declarations show the intended distinction:

~~~ts
{ prefix: 'gpt-image-2', values: {
    modalities: ['text', 'image', 'image_generation'],
    imageInputFidelity: { level: 'high' },
    // pricing omitted
} },
{ prefix: 'gpt-image-1.5', values: {
    modalities: ['text', 'image', 'image_generation'],
    imageInputFidelity: { level: 'high', requestValue: 'high' },
    // pricing omitted
} },
{ prefix: 'gpt-image-1-mini', values: {
    modalities: ['text', 'image', 'image_generation'],
    imageInputFidelity: { level: 'standard' },
    // pricing omitted
} },
{ prefix: 'gpt-image-1', values: {
    modalities: ['text', 'image', 'image_generation'],
    imageInputFidelity: { level: 'high', requestValue: 'high' },
    // pricing omitted
} },
~~~

The relevant Google image models and the supported Stability exact models are also declared with `level: 'high'` in the same workload.

The metadata is preserved as a single policy when provider defaults, exact matches, prefixes, contains rules, and fallbacks are merged:

~~~ts
imageInputFidelity: p.imageInputFidelity?.level
    ? {
        level: p.imageInputFidelity.level,
        ...(p.imageInputFidelity.requestValue
            ? { requestValue: p.imageInputFidelity.requestValue }
            : {}),
    }
    : fallback.imageInputFidelity,
~~~

Every relevant provider mapper writes `imageInputFidelity: modelDefaults.imageInputFidelity` into the `AiModel` record. This means the normal synchronization lifecycle updates both new and existing catalog rows.

## Metadata flow at runtime

The data path is:

`NEX model declarations -> AI_MODELS_LIST DynamoDB record -> AiModel lookup -> MediaGenerationMatrix/routed model metadata -> ProviderState -> ImageRouter/OpenAIProvider`

`services/api/src/llm/graph/state.ts` exposes a provider-neutral check:

~~~ts
export const hasHighImageInputFidelity = (meta: AiModelMetaInfo | undefined): boolean =>
    meta?.imageInputFidelity?.level === 'high'
~~~

`services/api/src/llm/tools/image-router.ts` enforces that policy only when Character Creator has a source reference and therefore requires the fidelity pass:

~~~ts
const requiresFidelityPass = state.capabilityUsageMode === 'character-creator'
    && sourceReferenceImages.length > 0

if (requiresFidelityPass && !hasHighImageInputFidelity(imageMeta)) {
    let modelLabel = imageModel
    if (typeof imageMeta.model === 'string') modelLabel = imageMeta.model
    if (typeof imageMeta.title === 'string') modelLabel = imageMeta.title
    throw new Error(
        'CHARACTER_CREATOR_REFERENCE_FIDELITY_UNSUPPORTED: '
        + `${modelLabel} does not advertise high-fidelity image input support; `
        + 'select an image model whose synchronized metadata declares high fidelity.',
    )
}
~~~

There is no `imageProvider === 'OpenAI'`, `startsWith('gpt-image-...')`, or equivalent model-specific condition in the router.

`services/api/src/llm/providers/openai-provider.ts` also stopped inferring request behavior from the model version. It reads the routed metadata and only emits the provider field when synchronization supplied a value:

~~~ts
const imageInputFidelity = args.state.aiModelMetaInfo.imageInputFidelity
const inputFidelityRequestValue = imageInputFidelity?.requestValue

// ...

...(inputFidelityRequestValue
    ? { input_fidelity: inputFidelityRequestValue }
    : {}),
~~~

The same conditional metadata application is used for the OpenAI Responses API image-generation tool. As a result, `gpt-image-2` is treated as high fidelity without sending an unsupported/unnecessary request value, while models configured with `requestValue: 'high'` receive the explicit field.

## Exact Anthropic model IDs from Bedrock

When `ANTHROPIC_USE_AWS_BEDROCK_INFERENCE=true`, the synchronization workload obtains available Anthropic models from Bedrock. Bedrock returns concrete snapshot IDs; those must be projected to the exact vendor snapshot ID rather than to an undated family alias.

`services/nex/workloads/ai-models-synchronization/ai-models-synchronization.ts` now does this projection explicitly:

~~~ts
private projectBedrockAnthropicModel(
    bedrockModelId: string,
    displayName: string | undefined,
): AnthropicModel | undefined {
    const match = /^anthropic\.(.+?)(?:-(\d{8}))?-v\d+(?::\d+)?$/i.exec(bedrockModelId)
    if (!match) return undefined

    const modelId = match[2] ? `${match[1]}-${match[2]}` : match[1]!
    return {
        id: modelId,
        display_name: displayName || modelId,
        ...(match[2] && {
            created_at: `${match[2].slice(0, 4)}-${match[2].slice(4, 6)}-${match[2].slice(6, 8)}`,
        }),
    }
}
~~~

Example:

`anthropic.claude-haiku-4-5-20251001-v1:0` becomes `claude-haiku-4-5-20251001`, not `claude-haiku-4-5`.

The shared Anthropic filter accepts an `includeSnapshots` flag. The vendor API path retains its existing moving-alias filtering, while the Bedrock path calls `filterAnthropicModels([...], true)` because concrete dated releases are the catalog entries Bedrock actually exposes. This restores the exact DynamoDB key expected by persisted selections such as `Anthropic:claude-haiku-4-5-20251001`.

## Character Creator behavior tied to this metadata

The Character Creator capability instructions and prompt builder were tightened so that a photographic source is an authoritative photorealistic reference. Any illustrated character in the sheet template is layout guidance and negative style evidence, not a style target.

The generation flow remains two-pass:

1. layout synthesis produces the sheet composition;
2. fidelity restoration may fully rerender the draft character pixels while preserving the non-character sheet layout.

The router only starts those passes after the routed image model advertises high fidelity.
