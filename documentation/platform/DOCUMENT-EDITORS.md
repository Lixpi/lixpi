# Document Kinds and Editors

Lixpi stores many kinds of ProseMirror documents: asset content, titles and metadata, conversation threads, provenance transcripts, the AI prompt input, Capability Artifacts and the sidebar outline. The API reads and writes them headlessly, and the browser edits them with different behavior per kind. Each document type is described once as a document kind, so the schema the API validates against is the schema the browser edits, and each browser view lists the features it runs instead of branching on the document type.

## Document kinds

A document kind, defined in `@lixpi/prosemirror` (`shared/document-kind.ts`), names its schema version, lists the schema bundles that supply its nodes and marks, declares its top node's content, and creates an empty document. A schema bundle is a named, reusable set of node and mark specs: `base-blocks`, `custom-blocks`, `prompt-reference`, `ai-chat`, `ai-prompt-input`, and `nested-list` from `@lixpi/prosemirror`. A bundle that changes an existing node, such as the custom code block, declares it as an override; two bundles that define the same node differently are refused.

A `DocumentKindRegistry` builds each kind's schema once when the kind registers, and rejects a kind registered twice. Each composition root builds its own registry from the kinds it uses: `createCoreDocumentKindRegistry` registers the six core kinds (`assetContent`, `assetTitle`, `assetMetadata`, `assetConversation`, `assetProvenance` and `aiPromptInput`), and `registerCapabilityArtifactDocumentKinds` adds every installed Capability Artifact as `capabilityArtifact:<artifactTypeId>`. The API resolves the kind for a stored document with `documentKindForAsset(asset, role)`, and the headless engine takes `{registry, kindId}`.

## Views and features

The browser half of a kind is a view definition: the kind id, an ordered list of features, and optionally the document to start with when the host has none. A feature is a named unit created once per view from the view's context; it can contribute plugins, node views, DOM event handlers, an editable rule and attributes. Feature order is plugin order.

`mountDocumentView` creates an `EditorView` from the kind's cached schema and the definition's features. Replacing the whole document, such as with a server copy, dispatches one replace transaction marked `skipDispatch` and kept out of history, so plugins and node views stay in place.

Editable documents mount through `mountDocumentEditor` instead. It adds a session that the editing features share: change callbacks, whether the view is read-only or disabled, and, for server-authored documents, the `DocumentAuthority`. The authority holds the asset's edit lease, sends local steps in batches, applies remote steps and rebases pending local ones over them, and resumes from the server after a gap. A view that edits through the authority stays read-only until the lease is granted and becomes read-only again when another workspace holds it. The authority reaches the server through a `DocumentAuthorityTransport` that the host implements; web-ui's transport adds the user's token to the NATS resume and submit requests and calls the asset service for leases and snapshots.

## Which package owns what

The packages depend in one direction, so another repository can take only the layers it needs.

| Package | Owns |
|---|---|
| `@lixpi/prosemirror` | Document kinds, bundles and registry; headless engine; editor views, synchronization and authority; rich-editing, chat, prompt and reference plugins/NodeViews; editor composition and styles; the generic nested-list plugin and navigation component; editor test fixtures |
| `@lixpi/prosemirror-themes` | The complete original `cm6-themes` tree, its eight theme packages, and Lixpi's themed Gruvbox Light variant |
| `@lixpi/canvas-components` | Canvas geometry, workspace UI and editor hosts that consume the public ProseMirror APIs; no editor plugin, NodeView or schema implementation |
| `@lixpi/capability-system` | Each Capability Artifact's kind (`documentKind`) and view (`documentView`) |
| `services/web-ui` | Workspace-specific item NodeViews, policies and sidebar adapter built on the generic nested-list plugin |
| `services/api` | Workspace hierarchy, authorization and navigation persistence; see [Workspace Tree](../canvas/WORKSPACE-TREE.md) |

Tests check the dependency direction: ProseMirror does not import canvas-components or Capability runtime implementation, and its shared/backend layers stay independent of browser features. Domain-specific extensions consume the package's public contracts.

## Ports

Features that need application services receive them through typed ports in the view's context, never by importing application code. The rich-editing features read `RichEditingPorts`: a media URL resolver, an optional image download and an optional model badge for generated media. The chat, prompt and reference editing features read `EditorServices` supplied by the host:

- `media`: the URL resolver, asset rendition paths, the model badge and image download
- `settings`: the editor settings supplied through the public editor contract
- `models`: the model catalog and the media generation config matrix, with change notifications
- `segments`: streamed response segments, routed by conversation
- `capabilityArtifacts`: host factories for Capability Artifact previews, icons and styles
- `previews`: host-owned reference chip creation; reference and message preview renderers supply callbacks without exposing canvas nodes
- `promptChrome`: host factories for prompt controls
- `createCapabilityRunProgress`: the progress panel for Capability runs
- `modelControls`: the prompt input's model menu and configuration matrix helpers

The prompt input also takes `PromptControlFactories`, the dropdowns, submit button and Capability controls the host builds from its own components. `@lixpi/prosemirror/frontend/editor` exports these editor integration contracts and `createPromptComposerHandle`. Canvas hosts use that handle to read/restore draft content, apply model preferences, insert references and focus/destroy the editor without manipulating ProseMirror state. Editor styles are exported from `@lixpi/prosemirror/styles/editor` and its named subpaths. Canvas preview geometry and styles remain host-owned.

## The view of each kind

`editorDocumentViews` defines the views web-ui mounts. Content, title and metadata documents run document sync and focus, then the bubble menu, link tooltip, image selection, prompt-reference node views and input rules, then the formatting key map, base key map, drop cursor, gap cursor, history and code blocks, and the editable rule last. Conversation and provenance threads add the AI chat thread after those features, and a conversation also binds Mod-Shift-I to insert a thread; an empty thread starts as one `aiChatThread` with the host's thread id. The prompt input runs the `@` reference picker, the `/` Capability module picker and the prompt input plugin ahead of the same editing features. `capabilityArtifactEditorView` wraps a module's own view in document sync, focus, prompt-reference node views, the base editing features and the `@` picker.

## Setting it up in a host

Web-ui keeps the composition in `services/web-ui/src/editor/`. `createWebUiEditorEnvironment` builds the registry (the core kinds plus installed Capability Artifacts), the editor services and the authority transport once; the canvas adapters pass it to `mountEditorDocument` with the view definition for the document and the per-mount options, such as the authority coordinates, the chat callbacks or the prompt controls.

Plugin implementation, NodeViews, supporting code and plugin-specific styles live together under `src/frontend/plugins`, including `ai-chat-thread`, `ai-prompt-input`, `prompt-reference`, `code-block`, `nested-list` and the rich-editing plugins. Public stylesheet exports point directly to those plugin-owned files. `src/styles` retains the shared document-view rules and editor stylesheet composition. The web-ui Capability-run and execution-trace renderers own their styles beside their components.

`src/frontend/editor` owns composition, host ports and handles; its public barrel assembles the plugin modules. Shared test fixtures, including editor service fixtures, live under `src/test-helpers` and use the `@lixpi/prosemirror/test-helpers` export.

A repository that needs nested-list navigation imports `mountNestedList` from `@lixpi/prosemirror/frontend/nested-list` and the shared `@lixpi/prosemirror/styles/nested-list` stylesheet. A caller that already owns its ProseMirror view can instead install `createNestedListPlugins` with the schema from `@lixpi/prosemirror/shared/nested-list`. Rich-text editors compose the features under `@lixpi/prosemirror/frontend/rich-editing` with their own view definition and `RichEditingPorts`. Chat and prompt integrations receive `EditorServices`; package tests supply editor-service fixtures.

## Nested-list navigation

The list subset uses ordinary paragraph, heading, bullet-list and list-item nodes. Paragraphs and headings appear outside complete lists. Each list item contains one paragraph title followed only by nested lists. A generic section container can group a protected title and complete document blocks; web-ui uses it for organization wrappers in the combined editor, without storing wrappers in per-organization documents. Serializable item attributes carry a stable entry id, an item type, optional JSON data and tag ids. The shared schema parses and validates these documents without loading browser views or a workspace service.

Plain items use the shared text-and-tags row. A consumer can register a ProseMirror NodeView constructor per item type through `itemViews`. Its `li` root and `contentDOM` keep text in ProseMirror while optional controls remain outside editable content. `createNestedListItemView` supplies a reusable shell for consumers that only need additional controls. Its first grid row contains the item label and right tags and consumer controls. A ProseMirror widget places the collapse button after the label text without storing it in the document. The shared base stylesheet keeps its invisible caret separator at zero width so application image sizing cannot add a blank line. The drag handle overlays the grid, while nested lists occupy subsequent rows without changing ProseMirror child order. The plugin forwards NodeView lifecycle and event hooks and recreates the view if the item type changes. No item is required to navigate or have a menu.

The mounted component owns view/edit mode, document reordering, transient collapse and active state. The first navigation click activates immediately, without waiting for a possible double click. A double click enters editing while its second click avoids duplicate activation. Drag completion suppresses its synthetic click separately. Ordinary clicks then edit text; Cmd/Ctrl+click invokes the consumer's activation callback. Escape, clicking outside or clicking unused editor background below the document nodes blurs the editor and returns to navigation without reverting changes. The background click is handled before native caret placement. Actual text blocks, including empty paragraphs, remain editable, and its own body-mounted BubbleMenu counts as inside. Double-clicking the empty editing area can still enter editing. In navigation mode, dragging anywhere within a row moves it; in edit mode, dragging text selects text and dragging non-text space moves the block. Plain list labels use ordinary list-item splitting. Consumers can register an Enter command per custom item type; a registered command owns that key even when it declines a mutation, so it cannot accidentally fall through to a plain item split. Standalone headings and paragraphs use ordinary text-block splitting; Enter at the end of a heading creates a paragraph and moves the caret into it. List-item moves carry their whole subtree. After the movement threshold, an inert copy of the dragged block follows the pointer above the interface, while the source remains hidden in its original space. The preview preserves typography and nesting and is removed on release, cancellation, window blur or destruction. Moving within the hidden source's occupied row or subtree shows no insertion slot and cannot change the document. Other destinations follow the current pointer over row bounds or the nearby gap; an enclosing group is not a substitute target. Release resolves that position again, and only a valid drop changes the document. Dragging preserves the current view or edit mode. A single accent line marks the insertion boundary for both list items and text blocks without changing block geometry. Nesting places the line below the target subtree and indents it to the child level. Dropping after a parent marks the boundary below its complete subtree. The menu trigger is hidden during dragging so it cannot intercept target lookup. Release resolves the current pointer target again; cancellation removes feedback without applying a move. Blank space at the editor edges resolves to the first permitted boundary, including inside a consumer-protected container. Escape cancels an unfinished drag and exits editing.

A single ui-kit dragIcon overlay serves hovered list rows, paragraphs and headings at a fixed far-left position. List rows place the 20px group collapse control 6px after the title text. Its circular hover and keyboard-focus background uses the selected-switch blue to distinguish collapse from row activation. The drag icon stays outside the row highlight, always uses the selected-item foreground, and reserves no layout space. Every block type starts the same drag controller through this handle, sharing its movement threshold, destination feedback, guards and cancellation. Groups keep chevronDownIcon visible, pointing down when expanded and rotated right when collapsed. Tags and consumer controls stay on the right. A verticalTrippleDots trigger overlays the hovered row or ordinary text block, inset 8px from the right edge without shifting content. Its size follows the shared dropdown trigger proportions. Clicking it opens the existing ui-kit BubbleMenu with icon controls and the vertical text-style selector without entering text editing or starting a drag. Opening the menu moves focus into its toolbar and hides the text caret while preserving the current mode, document and selection. Toolbar SVGs use the same per-item `iconSize` sizing mechanism as the rich editor; shared dropdown styles retain responsive icon sizing. Built-in insertion choices are Text, Heading 1, Heading 2 and Heading 3. Standalone text insertions are allowed at document or section boundaries before or after a complete list. They cannot enter item bodies or split an existing list around text. The `blockMenu` callback supplies custom insertion and action items for the current block; returning `null` suppresses controls for protected container labels. An item may supply an `icon` using existing SVG artwork while its `label` remains the accessible name. Items without icons retain text for variable choices such as tag names. The menu does not expose Bold or a separate Bulleted list option; actionable item insertions create the navigation list structure. Choosing a document-changing action enters editing and emits an accepted document change.

H1, H2 and H3 remain distinct semantic heading nodes. Their navigation presentation uses the existing compact h4/h5/h6 size tokens relative to the 14px list base, with zero vertical padding. Headings have a 0.8em top margin, except when a heading is the first content node, and a 0.2em bottom margin; ordinary body paragraphs have a 0.2em bottom margin. These small gaps scale with font size, while list-item labels keep their existing row spacing. Heading text and its menu trigger share the same vertical center; the full document-title scale does not apply to this compact surface.

Style conversion applies to standalone ordinary text blocks. A list-item label remains a paragraph, including custom actionable items. Whole-label bold uses the paragraph or heading's `bold` attribute; it is not partial inline formatting. Read-only mounts retain group collapse but expose neither the drag affordance nor the mutation menu.

A consumer supplies `filterTransaction` for domain guardrails and `onChange` for persistence. The filter applies to document mutations, including list commands and history. Keep it free of side effects. The shared schema and transaction checks enforce list integrity before consumer guards run, including typing, paste and history. Custom item Enter commands define domain-specific behavior in the consumer. The workspace adapter uses Enter to flush the current name and exit editing without inserting another item. Rejected edits do not produce accepted-change notifications. The component has no Save/Cancel session or save-time editing lock. Hosts own debounce, request sequencing, acknowledgements and error recovery. The generic package has no workspace deletion or routing rules.

The mount handle exposes its `EditorView`, mode, active and collapsed item controls, `enterEdit`, `exitEdit`, `setDocument`, `move` and `destroy`. `onChange` receives the previous and resulting ProseMirror documents and the accepted transactions. An incoming document returns `deferred` from `setDocument` while editing; after editing ends the host must still protect any unacknowledged local changes before replacing it. Autosave acknowledgement does not require a document replacement or history reset. Hosts with an outer scroll panel supply `scrollContainer`; pointer drags then scroll that panel near its edges and stop when the drag ends.

The same frontend export provides `moveNestedListBlock`, `moveNestedListItem`, `deleteNestedListItem`, `insertNestedListBlockBefore`, `insertNestedListBlockAfter` and `splitNestedListItem` commands. They preserve complete lists: standalone headings and paragraphs cannot be inserted or dropped between their items or inside an item body. `changeNestedListBlockStyle` converts standalone text blocks, and `toggleNestedListBlockBold` toggles the whole text block or item label. Consumers still authorize domain actions separately through their transaction policy.

The editor surface is transparent. List titles, headings and paragraphs retain an 18px base inset. Each additional list level adds 16px. The drag affordance overlays the far-left edge with a 3px inset at every nesting depth and reserves no text gutter. List-row hover and active backgrounds share a 14px left inset, an 8px right inset and rounded corners across the sidebar width, leaving the drag icon outside the colored area. Selected rows use the image/video mode toggle's indicator blue and selected foreground. Hovered rows use its track blue and inactive foreground. The selected background uses the indicator color alone, avoiding the stronger tint produced by layering it over the track. The state foreground applies to the row label, chevron and right-side controls. The drag overlay always uses the selected-item foreground and fill. A parent's state covers only its own row; descendants remain independent. Paragraphs and headings have no hover background. Ordinary text blocks use the default cursor in navigation mode and the text cursor in editing mode. Each host applies the pointer cursor only to its actionable labels.

The actual design-system sidebar uses this component with `readOnly: true`, its catalog item types and its router. Its navigation wrapper adds no padding around the editor; the shared editor owns content spacing. The interactive Nested list example uses the same package with local fixture state. The workspace sidebar supplies workspace bindings, guards and revisioned persistence as described in [Workspace Tree](../canvas/WORKSPACE-TREE.md).

CodeMirror themes live in `@lixpi/prosemirror-themes`. Its `cm6-themes/` directory preserves the complete original tree, including the eight individual packages, their source, manifests, READMEs and support files. Each original theme is exported as `@lixpi/prosemirror-themes/<name>`; the package root re-exports them. The code-block editor uses the Lixpi variant at `@lixpi/prosemirror-themes/lixpi-gruvbox-light`, whose colors follow theme tokens. The nested vendor workspace is retained as source and is not registered as a separate installation workspace.
