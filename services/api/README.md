
# API

The [version registry](../../dev-tools/versions-registry/README.md) supplies Node.js, pnpm, and package versions. Edit the central values and synchronize the native declarations before rebuilding this image.

Organization Blob bytes live in native NATS Object Store buckets named `blobs-<organization>-files`. Document steps, pipeline events, Capability run events and maintenance jobs use native JetStream streams and consumers. The API uses `@lixpi/nats-service` directly for object reads/writes, event publication and replay. Domain metadata remains in DynamoDB. See [Data Storage](../../documentation/platform/DATA-STORAGE.md) for the data model and [NATS Cluster](../../documentation/platform/deployment/NATS-CLUSTER.md) for replication, retained volumes, snapshots and recovery.

The native storage acceptance test exercises API Blob writes, event sequencing, replay and workqueue acknowledgements against a disposable NATS broker. Commands and isolation requirements are in the [TypeScript testing guide](../../documentation/code-quality/testing/TYPESCRIPT.md).

Conversational transcripts use the existing ProseMirror document authority. Accepted user fragments and persisted assistant chunks are projected with the shared Markdown stream assembler into native steps. The first provider text starts a durable flush immediately. Later text is coalesced at 128 characters or 100 ms, with one write in flight; model and tool boundaries drain pending text before continuing. Each batch checks the active turn continuation in its commit so a stop or steering change cannot admit late text. Each projection commits its document pointer, actual step-count version and publication outbox under the conversation owner fence. JetStream publication uses stable step identities; recovery drains committed steps before continuing a turn, and the read-only editor receives them through the ordinary document relay and resume path. Delivered step payloads are released, and Asset deletion removes any retained projection payloads. Configuration messages retain their audit content and semantic role in the document while the shared message renderer keeps them out of the visible conversation. Equivalent settings updates do not advance the revision or publish another configuration event. A failed turn appends a typed failure message, keeping any partial assistant response separate. Stopped and failed turns retain their partial text without leaving it marked as receiving. The shared response NodeView presents that message as an error state. Projection restores this metadata on older failure records from their durable error events without classifying ordinary text as an error.

An accepted pipeline continuation retains its exact pipeline, frozen sources and succeeded operation outputs across context-mode changes. Every source still requires current Asset access and matching content. This execution scope exists only while advancing that pipeline; new model tools use the narrowed conversation context. Succeeded output admission commits with the operation receipt, so downstream mutations and later recovery can use the same authorized outputs.

Media sequence revisions retain each source Blob and check its Asset revision in the same transaction as the document, catalog title and mutation receipt. A sequence supports at most 24 source bindings. Artifact commits count source pins, Asset projections and revision bookkeeping before writing, reserving one DynamoDB operation for the account admission fence. An oversized commit returns `ARTIFACT_TRANSACTION_LIMIT` without advancing the revision.

Media exports persist a validated worker receipt and retain the encoded Blob before committing the output Asset. Finalization retries reuse that receipt and encoded output; they do not request another render. Cancellation and Asset cleanup release the output pin with the job's source references.

Canvas attachment retries bounded Asset and reference conflicts, including a rendition completing while an upload is placed. Each retry rereads authorization, lifecycle, references and canvas state before rebuilding the atomic transaction. A changed canvas still requires the caller to reconcile its placement.

Provider calls use `ProviderUsageClient` for pre-call authorization and measured-usage recording. The NATS subject and JSON contracts are documented in [`@lixpi/usage-reporter`](../../packages/lixpi/usage-reporter/README.md) and require a paired responder release.

Enabled metering prepares the replicated `PROVIDER_USAGE_OUTBOX` JetStream workqueue before serving requests. Usage and completion messages persist before delivery and retry across API or responder restarts. The worker acknowledges them only after the responder confirms recording or completion. Auxiliary structured model calls carry the authorized chat, Capability or Asset caller's usage identity and authorize each attempt separately, including output-truncation retries. Unknown provider outcomes remain unresolved for reconciliation.

Denied media authorization settles the request and its reserved canvas output as failed. If the output Asset has not been created, the request service projects the failure onto the reservation and removes the duplicate operation card. The user sees the authorization error instead of a running spinner.

`user.preferences.update` accepts an appearance preset or agent behavior for the authenticated user. The write checks that the user exists and commits with the account admission condition. Appearance and agent behavior occupy separate attributes so concurrent updates to different sections can both commit. `user.get` reads the current values for the browser. Conversation submission reads the sending user's agent preference before accepting each turn.

`organization.membership.get` is a service-only NATS request that accepts `{ token, organizationId }`. The JWT middleware verifies this token freshly on every request and replaces any supplied user identity with the verified subject. A strongly consistent organization read returns only `{ organizationId, userId, name, accessLevel }` for the caller's own membership. Missing members, invalid tokens, and unavailable data fail closed. The responder has no browser permission grant and never returns an access list.

The API's JWT middleware requires an application token on NATS requests. Connection admission belongs to the embedded Go broker in `services/nats`; the API has no callout subscription or middleware exemption. It connects as `svc:api` using `NATS_API_NKEY_SEED` after applying the signed application manifest through a separate restricted bootstrap connection. Startup receives `NATS_APPLICATION_REGISTRATION` and `NATS_REGISTRATION_PASSWORD`; the authority signing seed and callout issuer/decryption seeds remain outside the API. Registration failure aborts startup before the application connection opens.

Local Compose startup also waits for the DynamoDB initializer to finish. In mock mode that initializer loads and validates the [fixed development account](../localauth0/README.md#automatic-initialization); a partial fixture prevents dependent API startup until explicitly repaired. Real-Auth0 mode skips the mock fixture. This is a Compose setup dependency; admission enforcement on application requests remains a separate authentication concern.

HTTP and NATS authentication read completed registration on every request and never create or repair accounts. Local mock requests read the fixed fixture's admission, user, organization and membership even when the hosted release gate is disabled. Real Auth0 requests require `ACCOUNT_ADMISSION_ENABLED=true` and a ready admission runtime. Requests that reach the runtime readiness gate during startup, control-feed interruption, or replay backlog receive `ACCOUNT_ADMISSION_UNAVAILABLE`; the request cannot run, but the browser retains its authenticated session for retry. Registration comes from the separately deployed hosted integration; an absent, incomplete, or blocked account returns `ACCOUNT_ADMISSION_DENIED`, which closes the browser session.

When `ACCOUNT_ADMISSION_STREAM` is configured, API startup prepares its durable JetStream feed before enabling admission. Configure the same stream name and signed permissions for its external publisher and consumers. The feed retains all control events, uses the configured replica count, and denies deletion and purging. An incompatible existing stream aborts startup without changing its settings or events. Stream preparation does not enable hosted authentication.

The coordinated hosted-signup release uses `ACCOUNT_ADMISSION_ENABLED=true` and a matching signed browser profile naming `ACCOUNT_ADMISSION_STREAM`. The [account admission validator](src/services/account-admission.ts) transactionally reads the authenticated subject's admission receipt, user, organization, and owner membership against the signed epoch. Its database port exposes no writer. Each API instance replays the durable control stream independently before accepting account policy checks or user requests. Stream loss closes admission and aborts active request scopes. The private broker responder binds each decision to its nonce, client key, registration digest and finite lease.

In the dev container nodemon restarts the API when one of its own sources changes. Shared packages restart it only when it loaded the edited file. `scripts/record-loaded-modules.mjs`, loaded with `node --import`, lists every package file the API loads in `/dev/shm`. `scripts/watch-loaded-modules.mjs` polls those files and touches the restart file nodemon watches when one changes. An edit to a file only the browser uses, such as a canvas setting, reloads the page without taking the API down, so open pages keep their connections. After a crash the watcher keeps running, so fixing a shared file restarts the API as before.

Local admission processes set their full consumer name as an immutable process title before registering with NATS. The nodemon launcher reserves enough argument space for that title; a truncated title prevents admission startup. External lifecycle controllers can use this identity to distinguish a stopped child from its replacement. Deployed processes use their ECS task and runtime container identities.

`GET /health-check` includes `accountAdmission` with the live readiness flag, issuer, signed application-registration digest and process identity. When enforcement is enabled, an unavailable control feed makes health return HTTP 503. The response contains no credentials or account records. The local release checks this response on each discovered API process before binding signup.

Each control consumer records its process role and deployment identity. Local processes use their Docker container ID; deployed processes read their container ID and task ARN from the fixed ECS metadata endpoint. A missing or invalid identity prevents control-feed startup. Consumers remain stored after a process disappears so enforcement can distinguish an unresponsive process from a deployment confirmed stopped.

The stored verification source can be a Passwordless email code, a database code, Auth0's native enterprise email code, trusted social verification, or a consumed hosted Form challenge. Native proofs must match the stored provider mailbox; Form proofs must retain their challenge and provider identity binding. The API validates the receipt written by the provisioner and does not infer verification from browser profile fields.

Control events use `active`, `blocked`, `reconciling`, or `superseded`. The external account service publishes these decisions. The feed and request scopes share this event type; private stored-state names do not extend the wire contract.

[Account request context](src/services/account-request-context.ts) associates verified claims with middleware payloads without accepting identity claims from JSON fields. It keeps NATS handlers and their replies inside an indexed scope. HTTP scopes remain active until the response finishes, close the response on cancellation and reject late writes. Detached conversation, matrix and Capability jobs recheck the same verified identity in their own scope, and their provider/action signals include account cancellation. Bound terminal cleanup releases the existing lease and cancels or fails unfinished records without accepting another identity or resource. The release gate defaults to false; hosted signup, lifecycle administration, worker cancellation and accounting must be ready before activation.

The API's [database adapter](src/services/account-database-service.ts) uses the [account committer](src/services/account-committer.ts) to add a read-only admission condition to each user transaction. The condition binds the scope's identity, active state, epoch, and personal organization and rejects operation locks, aliases, or blocking intent. Resource conditions remain in their original operations. Scoped model updates use this transaction path; ordinary single-item and batch-write entry points reject user scopes. A user transaction cannot write the admission table, and a failed condition never retries as an unguarded write. Cancellation reaches the SDK and rejects late acknowledgements; it cannot undo a transaction committed before disabling.

Organization membership and workspace, Asset and Capability access-list writes also check each target user's active admission state in the same transaction. Targets are deduplicated, and the requester's existing epoch condition covers grants to that requester. This prevents a concurrent grant from escaping a recipient's reconciliation lock. A healthy control-feed backlog pauses new admission without cancelling unrelated scopes; control-feed loss cancels them.

Workspaces form a tree. The API's `src/services/workspace-navigation/` domain owns its rules, storage access and request handlers, and `src/services/workspace-tree-service.ts` composes them with the API's organizations, its conversation stop and its per-workspace cleanup. The workspace subjects bind those handlers beside the API's own workspace read and canvas save; a create request without an organization uses the user's first one. Startup finishes interrupted navigation saves, external mutations, moves, rebalances and subtree deletes from the organization's recorded operation. `WORKSPACE_TREE` stores each parent's ordered children, `WORKSPACE_TREE_LOCKS` holds at most one running structure operation per organization, and `WORKSPACES_ACCESS_LIST` is the only record of grants, with a `workspaceId-userId` index for listing a workspace's grants. Their key schemas live in `aws-resources.ts` in `@lixpi/constants`, so Pulumi and the local table initializer build the same tables. The local initializer adds a missing index to a preserved table without recreating it.

Workspace navigation has one canonical nested-list document per organization. `workspace.getUserWorkspaceNavigation` returns the caller's authorized document projection and revision; `workspace.saveWorkspaceNavigation` validates the current document against that revision. The request explicitly identifies authorized workspace creations and deletions, and the document determines labels, tags and the nearest enclosing workspace parent. New workspace IDs are conditionally reserved with an operation-specific creation identity so recovery cannot adopt a workspace created by another request or organization. A creation collision removes only that operation's unpublished creations and leaves the saved revision intact. Empty paragraphs and headings remain valid identified blocks outside complete lists. Each list item contains one paragraph label and optional nested lists. Domain text placement cannot split an existing menu list, and list-item labels cannot become headings. Organization section wrappers belong only to the composed UI document. Whole-label bold formatting is retained in the canonical document, including through external workspace and heading mutations; workspace names in metadata remain plain text.

Navigation autosave uses `workspacePersistenceSettings.debounceMs` from `@lixpi/constants`, currently 3000 ms. This shared setting is separate from the ProseMirror asset editor's 100 ms collaboration-step batching. API `settings.navigationPersistence` independently limits accepted requests to a burst of six per authenticated user, replenishing one request every 3000 ms across all organizations. A strongly consistent, conditional transaction updates one reusable `USER#<userId>#NAVIGATION` / `WRITE_ADMISSION` record in `WORKSPACE_TREE`; the application's account-admission fence still applies. The record contains only its key and next-admission timestamp, needs no TTL or new table, and regains its full burst after inactivity. Conditional contention retries stop after three attempts. Throttled responses carry `WORKSPACE_NAVIGATION_RATE_LIMITED` and a positive `retryAfterMs` in milliseconds; clients retain the exact mutation payload and ID while waiting. Retries also consume admission capacity. The `workspaceNavigationWrites` NATS queue sends each autosave request to one API replica, so replicas do not multiply that admission charge.

Before recursive schema parsing or JSON serialization, the API bounds raw navigation input iteratively. Defaults allow 512 KiB of serialized document JSON, 4096 document nodes, depth 64, and a combined 128 explicit workspace creation/deletion IDs. Individual text limits and workspace permission checks still apply. A semantically unchanged document records its mutation receipt atomically against the current head with no running organization operation, without creating another revision. A reused mutation ID still requires the same user and request hash, including when an unchanged acknowledgement races a changed document. A successful retry reauthorizes access and returns the current authorized snapshot, which may include subsequent edits; it does not replay an old document projection. Clients must detect a differing acknowledgement and retain their local work for conflict recovery.

The navigation repository stages immutable JSON chunks in `WORKSPACE_TREE`, applies the derived hierarchy under the organization's recoverable lock, and commits the document head and mutation receipt last. Workspace metadata reads use strongly consistent transactions, while access, tree and delegation reads check the lock and head before and after their traversal. Explicit deletion first applies surviving workspace moves, then runs the existing conversation stop and content cleanup. A workspace's final parent index, full row and meta row are removed together so recovery can still find every unfinished descendant. Existing external workspace mutation subjects use the same locked publication path.

The first authorized navigation read or domain mutation initializes an empty revision zero under the organization lock. A missing canonical head with existing hierarchy rows is an integrity error. Domain note metadata is independent of navigation; mutations do not inject note paragraphs into menu items. The sidebar exposes workspace labels and tags without a separate note feature. Previous revisions and unreferenced staged chunks are retained; there is no automatic revision garbage collection. See [Workspace Tree](../../documentation/canvas/WORKSPACE-TREE.md) for the document, permission and recovery contracts.

Asset lease acquisition records the authenticated editor's user ID on each holder, and renewal retains it. Account maintenance uses that identity to release suspended editors without removing a collaborator's holder. Existing holders without an identity remain valid until expiry and delay migration while active.

`@lixpi/nats-subject-registry` defines the active endpoint groups, their `permissions`, and built-in service permissions. Contract IDs and handler-map keys come from `getNatsSubjectPath()` in `@lixpi/constants`; subject names and wire values are declared only in the constants package. `createNatsSubscriptions()` in `create-nats-subscriptions.ts` creates subscriptions from these declarations and their handlers, rejecting missing or extra handlers. Deployment setup signs the registry's declarations and configured identities. API startup submits those approved bytes before creating subscriptions. Refresh the signed manifest when endpoint grants or service identities change; the Go broker image is independent of the application contract.

The local authentication integration test uses the running API, embedded NATS cluster, and LocalAuth0. It requests the mock authorization page with the login parameters and verifies that its preloaded JavaScript, snippets and WebAssembly share a versioned URL prefix. It checks every asset's integrity hash and validates the WebAssembly, then checks the fixed identity and structured admission claim. It rejects invalid connection credentials, connects with a fresh local token and user-scoped inbox, rejects missing/invalid request tokens, reads the authenticated user's profile and workspace tree, and creates, reads, renames, and deletes its own temporary workspace. It uses HTTP and TCP NATS and does not inspect a browser. With those local services running and test execution permitted by `CODING_AGENTS_TEST_EXECUTION_MODE` in `env.lixpi`, run:

```bash
docker compose --env-file .env.<stage> -f infrastructure/docker/utilities/code-quality/docker-compose.typescript-test-runner.yml --profile dev run --rm --no-deps -T -e LIXPI_NATS_RUNTIME_TEST=true lixpi-typescript-test-runner api src/NATS/middleware/nats-auth-middleware.runtime.test.ts
```

The test is skipped during ordinary unit-test runs.

Browser permissions are supplied to the auth callout separately from responder registration. Generic module requests and events use the authenticated user's hex token. Both browser applications also configure `_INBOX.<user-token>` as their reply prefix. Deployment setup incorporates `NATS_SERVICE_AUTH_REGISTRATIONS` into the signed runtime manifest; see [Authentication](../../documentation/platform/AUTHENTICATION.md).
