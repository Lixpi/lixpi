
# API

The [version registry](../../dev-tools/versions-registry/README.md) supplies Node.js, pnpm, and package versions. Edit the central values and synchronize the native declarations before rebuilding this image.

Organization Blob bytes live in native NATS Object Store buckets named `blobs-<organization>-files`. Document steps, pipeline events, Capability run events and maintenance jobs use native JetStream streams and consumers. The API uses `@lixpi/nats-service` directly for object reads/writes, event publication and replay. Domain metadata remains in DynamoDB. See [Data Storage](../../documentation/platform/DATA-STORAGE.md) for the data model and [NATS Cluster](../../documentation/platform/deployment/NATS-CLUSTER.md) for replication, retained volumes, snapshots and recovery.

The native storage acceptance test exercises API Blob writes, event sequencing, replay and workqueue acknowledgements against a disposable NATS broker. Commands and isolation requirements are in the [TypeScript testing guide](../../documentation/code-quality/testing/TYPESCRIPT.md).

Provider calls use `ProviderUsageClient` for pre-call authorization and measured-usage recording. The NATS subject and JSON contracts are documented in [`@lixpi/usage-reporter`](../../packages/lixpi/usage-reporter/README.md) and require a paired responder release.

Enabled metering prepares the replicated `PROVIDER_USAGE_OUTBOX` JetStream workqueue before serving requests. Usage and completion messages persist before delivery and retry across API or responder restarts. The worker acknowledges them only after the responder confirms recording or completion. Auxiliary structured model calls carry the authorized chat, Capability or Asset caller's usage identity and authorize each attempt separately, including output-truncation retries. Unknown provider outcomes remain unresolved for reconciliation.

Denied media authorization settles the request and its reserved canvas output as failed. If the output Asset has not been created, the request service projects the failure onto the reservation and removes the duplicate operation card. The user sees the authorization error instead of a running spinner.

`organization.membership.get` is a service-only NATS request that accepts `{ token, organizationId }`. The JWT middleware verifies this token freshly on every request and replaces any supplied user identity with the verified subject. A strongly consistent organization read returns only `{ organizationId, userId, name, accessLevel }` for the caller's own membership. Missing members, invalid tokens, and unavailable data fail closed. The responder has no browser permission grant and never returns an access list.

The API's JWT middleware requires an application token on NATS requests. Connection admission belongs to the embedded Go broker in `services/nats`; the API has no callout subscription or middleware exemption. It connects as `svc:api` using `NATS_API_NKEY_SEED` after applying the signed application manifest through a separate restricted bootstrap connection. Startup receives `NATS_APPLICATION_REGISTRATION` and `NATS_REGISTRATION_PASSWORD`; the authority signing seed and callout issuer/decryption seeds remain outside the API. Registration failure aborts startup before the application connection opens.

Local Compose startup also waits for the DynamoDB initializer to finish. In mock mode that initializer loads and validates the [fixed development account](../localauth0/README.md#automatic-initialization); a partial fixture prevents dependent API startup until explicitly repaired. Real-Auth0 mode skips the mock fixture. This is a Compose setup dependency; admission enforcement on application requests remains a separate authentication concern.

HTTP and NATS authentication read completed registration on every request and never create or repair accounts. Local mock requests read the fixed fixture's admission, user, organization and membership even when the hosted release gate is disabled. Real Auth0 requests are denied until `ACCOUNT_ADMISSION_ENABLED=true` and the admission runtime is ready. Registration comes from the separately deployed hosted integration; an absent or incomplete account receives the same admission denial as a blocked account.

When `ACCOUNT_ADMISSION_STREAM` is configured, API startup prepares its durable JetStream feed before enabling admission. Configure the same stream name and signed permissions for its external publisher and consumers. The feed retains all control events, uses the configured replica count, and denies deletion and purging. An incompatible existing stream aborts startup without changing its settings or events. Stream preparation does not enable hosted authentication.

The coordinated hosted-signup release uses `ACCOUNT_ADMISSION_ENABLED=true` and a matching signed browser profile naming `ACCOUNT_ADMISSION_STREAM`. The [account admission validator](src/services/account-admission.ts) transactionally reads the authenticated subject's admission receipt, user, organization, and owner membership against the signed epoch. Its database port exposes no writer. Each API instance replays the durable control stream independently before accepting account policy checks or user requests. Stream loss closes admission and aborts active request scopes. The private broker responder binds each decision to its nonce, client key, registration digest and finite lease.

Local admission processes set their full consumer name as an immutable process title before registering with NATS. The nodemon launcher reserves enough argument space for that title; a truncated title prevents admission startup. External lifecycle controllers can use this identity to distinguish a stopped child from its replacement. Deployed processes use their ECS task and runtime container identities.

`GET /health-check` includes `accountAdmission` with the live readiness flag, issuer, signed application-registration digest and process identity. When enforcement is enabled, an unavailable control feed makes health return HTTP 503. The response contains no credentials or account records. The local release checks this response on each discovered API process before binding signup.

Each control consumer records its process role and deployment identity. Local processes use their Docker container ID; deployed processes read their container ID and task ARN from the fixed ECS metadata endpoint. A missing or invalid identity prevents control-feed startup. Consumers remain stored after a process disappears so enforcement can distinguish an unresponsive process from a deployment confirmed stopped.

The stored verification source can be a Passwordless email code, a database code, Auth0's native enterprise email code, trusted social verification, or a consumed hosted Form challenge. Native proofs must match the stored provider mailbox; Form proofs must retain their challenge and provider identity binding. The API validates the receipt written by the provisioner and does not infer verification from browser profile fields.

Control events use `active`, `blocked`, `reconciling`, or `superseded`. The external account service publishes these decisions. The feed and request scopes share this event type; private stored-state names do not extend the wire contract.

[Account request context](src/services/account-request-context.ts) associates verified claims with middleware payloads without accepting identity claims from JSON fields. It keeps NATS handlers and their replies inside an indexed scope. HTTP scopes remain active until the response finishes, close the response on cancellation and reject late writes. Detached conversation, matrix and Capability jobs recheck the same verified identity in their own scope, and their provider/action signals include account cancellation. Bound terminal cleanup releases the existing lease and cancels or fails unfinished records without accepting another identity or resource. The release gate defaults to false; hosted signup, lifecycle administration, worker cancellation and accounting must be ready before activation.

The API's [database adapter](src/services/account-database-service.ts) uses the [account committer](src/services/account-committer.ts) to add a read-only admission condition to each user transaction. The condition binds the scope's identity, active state, epoch, and personal organization and rejects operation locks, aliases, or blocking intent. Resource conditions remain in their original operations. Scoped model updates use this transaction path; ordinary single-item and batch-write entry points reject user scopes. A user transaction cannot write the admission table, and a failed condition never retries as an unguarded write. Cancellation reaches the SDK and rejects late acknowledgements; it cannot undo a transaction committed before disabling.

Organization membership and workspace, Asset and Capability access-list writes also check each target user's active admission state in the same transaction. Targets are deduplicated, and the requester's existing epoch condition covers grants to that requester. This prevents a concurrent grant from escaping a recipient's reconciliation lock. A healthy control-feed backlog pauses new admission without cancelling unrelated scopes; control-feed loss cancels them.

Asset lease acquisition records the authenticated editor's user ID on each holder, and renewal retains it. Account maintenance uses that identity to release suspended editors without removing a collaborator's holder. Existing holders without an identity remain valid until expiry and delay migration while active.

`@lixpi/nats-subject-registry` defines the active endpoint groups, their `permissions`, and built-in service permissions. Contract IDs and handler-map keys come from `getNatsSubjectPath()` in `@lixpi/constants`; subject names and wire values are declared only in the constants package. `createNatsSubscriptions()` in `create-nats-subscriptions.ts` creates subscriptions from these declarations and their handlers, rejecting missing or extra handlers. Deployment setup signs the registry's declarations and configured identities. API startup submits those approved bytes before creating subscriptions. Refresh the signed manifest when endpoint grants or service identities change; the Go broker image is independent of the application contract.

The local authentication integration test uses the running API, embedded NATS cluster, and LocalAuth0. It verifies the mock login loader, JavaScript integrity, and valid WebAssembly, then checks the fixed identity and structured admission claim. It rejects invalid connection credentials, connects with a fresh local token and user-scoped inbox, rejects missing/invalid request tokens, reads the authenticated user's profile and workspace list, and creates, reads, renames, and deletes its own temporary workspace. It uses HTTP and TCP NATS and does not inspect a browser. With those local services running and test execution permitted by `CODING_AGENTS_TEST_EXECUTION_MODE` in `env.lixpi`, run:

```bash
docker compose --profile dev --profile main run --rm --no-deps -T -e LIXPI_NATS_RUNTIME_TEST=true lixpi-typescript-test-runner api src/NATS/middleware/nats-auth-middleware.runtime.test.ts
```

The test is skipped during ordinary unit-test runs.

Browser permissions are supplied to the auth callout separately from responder registration. Generic module requests and events use the authenticated user's hex token. Both browser applications also configure `_INBOX.<user-token>` as their reply prefix. Deployment setup incorporates `NATS_SERVICE_AUTH_REGISTRATIONS` into the signed runtime manifest; see [Authentication](../../documentation/platform/AUTHENTICATION.md).
